Mail Servers, Exchange & DNS Records — Study & Implementation Guide

1. The Big Picture: How Email Actually Travels

Before diving into records, understand the two email protocols that matter:

  • SMTP (Simple Mail Transfer Protocol, port 25/587/465) — used to send mail between servers, and from a client to a server.
  • IMAP/POP3 (or MAPI/EWS for Exchange) — used to retrieve mail from a mailbox.

When you send an email to someone@company.com, here's the actual sequence:

  1. Your mail client hands the message to your outgoing mail server (SMTP).
  2. That server needs to find where company.com receives mail. It queries DNS for an MX record on company.com.
  3. DNS returns the hostname of the receiving mail server (e.g., company-com.mail.protection.outlook.com).
  4. Your server does an A/AAAA lookup on that hostname to get an IP address.
  5. Your server connects via SMTP (port 25) to that IP and delivers the message.
  6. The receiving mail server (Exchange Online/On-Prem, or any SMTP gateway) accepts it, runs spam/malware filtering, and drops it into the mailbox.

Everything below (MX, CNAME, SPF, DKIM, DMARC, Autodiscover) exists to make this handoff correct, secure, and trusted.

2. MX Records (Mail Exchanger)

Purpose: Tells the internet which server(s) accept mail for your domain.

Format:

company.com.   MX   10   company-com.mail.protection.outlook.com.
  • Priority number (10) — lower number = higher priority. Mail servers try the lowest number first, and fall back to higher numbers if the first is unreachable.
  • You can have multiple MX records for redundancy:
company.com.   MX   10   mx1.company.com.
company.com.   MX   20   mx2.company.com.   (backup)
  • The MX record points to a hostname, never directly to an IP — that hostname must then resolve via an A record.

Key exam/real-world facts:

  • MX records live at the domain apex (the root, e.g. company.com), not on a subdomain, unless you're specifically routing mail for a subdomain.
  • In Microsoft 365, when you add a custom domain, Microsoft gives you an MX value like company-com.mail.protection.outlook.com — you must set this in your DNS provider (GoDaddy, Cloudflare, etc.), not in Microsoft.
  • If MX is missing or wrong, inbound mail fails entirely — this is one of the most common "we stopped receiving email" tickets.

3. CNAME Records (Canonical Name)

Purpose: An alias — points one hostname to another hostname (not an IP).

Format:

autodiscover.company.com.   CNAME   autodiscover.outlook.com.

Why CNAME matters for email specifically (Microsoft 365 / Exchange):

CNAME record Points to Why it exists
autodiscover.company.com autodiscover.outlook.com Lets Outlook clients auto-configure server settings just from an email address
selector1._domainkey.company.com selector1-company-com._domainkey.<tenant>.onmicrosoft.com DKIM signing (see below)
selector2._domainkey.company.com selector2-company-com._domainkey.<tenant>.onmicrosoft.com DKIM key rotation pair
sip.company.com sipdir.online.lync.com Teams/Skype for Business federation (legacy)
lyncdiscover.company.com webdir.online.lync.com Teams client discovery

Important distinction from MX: A CNAME cannot coexist with other records on the same name (e.g., you can't have both an MX and a CNAME on the exact same hostname), and CNAME can never point to an IP — only to another name that itself eventually resolves to an A/AAAA record.

4. Exchange (Server vs Online) — What It Actually Does

Exchange is the mail server software/service that stores mailboxes, applies mail flow rules, and handles calendar/contacts (via MAPI/EWS/ActiveSync).

  • Exchange Server (on-prem) — you run it yourself on Windows Server. You own the MX record pointing to your own public IP/firewall, you manage the Edge Transport role or a smart host, and you're responsible for spam filtering, patching, and certificates.
  • Exchange Online (part of Microsoft 365) — Microsoft hosts it. Your DNS MX record points to Microsoft's filtering front door (Exchange Online Protection / EOP), which scans mail before it lands in mailboxes.
  • Hybrid Exchange — some mailboxes on-prem, some in the cloud, connected via a Hybrid Configuration Wizard; mail routing between the two uses a connector that trusts the on-prem server's IP.

Core Exchange components to know for AZ-104 / support work:

  • Mailbox — the actual store of mail, calendar, contacts.
  • Transport rules (mail flow rules) — if/then logic applied to messages in transit (e.g., "if subject contains 'Confidential', encrypt").
  • Connectors — define trusted paths for mail in/out (e.g., an on-prem device that needs to relay through Microsoft 365 without authentication, like a scanner or app).
  • Accepted domains — domains Exchange Online is configured to receive mail for (this must match your MX target).
  • Exchange Online Protection (EOP) — the spam/malware/phishing filter that sits in front of every inbound message.

5. SPF, DKIM, DMARC — The Trust Layer (you'll be asked about these alongside MX/CNAME)

These three work together to stop spoofing and are graded together by receiving mail servers.

SPF (Sender Policy Framework) — a TXT record

company.com.   TXT   "v=spf1 include:spf.protection.outlook.com -all"

Declares which servers are allowed to send mail as your domain. -all = hard fail anything not listed (strict); ~all = soft fail (flag but don't reject).

DKIM (DomainKeys Identified Mail) — CNAME records (as shown above)

Cryptographically signs outgoing mail with a private key; the receiving server checks the signature against a public key published via those CNAME records. Proves the message wasn't altered in transit and really came from an authorized sender.

DMARC (Domain-based Message Authentication) — a TXT record

_dmarc.company.com.   TXT   "v=DMARC1; p=quarantine; rua=mailto:dmarc-reports@company.com"

Tells receiving servers what to do if SPF/DKIM checks fail (p=none/quarantine/reject) and where to send reporting data. This is the record that actually enforces the other two.

Why this matters together: MX tells the world where to deliver mail to you. SPF/DKIM/DMARC tell the world what mail is legitimately from you. Missing SPF/DKIM/DMARC is why company domains get spoofed in phishing campaigns, and it's a very common cause of "our emails are landing in recipients' spam" tickets.

6. How It All Works Together — Full Picture

flowchart TD
    A[Sender's mail server] -->|1. DNS query: MX for company.com| B[DNS]
    B -->|2. Returns mail.protection.outlook.com priority 10| A
    A -->|3. DNS query: A record for that host| B
    A -->|4. SMTP connect + deliver| C[Exchange Online Protection]
    C -->|5. Checks SPF/DKIM/DMARC against sender domain's DNS| B
    C -->|6. Spam/malware filter| D[Exchange Online Mailbox]
    E[Outlook client] -->|Autodiscover CNAME lookup| B
    E -->|Connects via MAPI/EWS| D

7. Implementing This at a Company (Practical Walkthrough)

This is the exact sequence you'd follow onboarding a company domain to Microsoft 365 — useful both for real work and as a mental model for exam scenarios.

  1. Add the custom domain in Microsoft 365 admin center (or Entra ID > Custom domain names).
  2. Verify domain ownership — Microsoft gives you a TXT record to add first (proves you control the DNS zone).
  3. Add the MX record Microsoft provides, pointing to <domain-key>.mail.protection.outlook.com, priority 0.
  4. Add SPF (TXT) — v=spf1 include:spf.protection.outlook.com -all.
  5. Add the two DKIM CNAMEs (selector1/selector2._domainkey), then enable DKIM signing in Defender/Exchange admin center — it's created disabled by default.
  6. Add DMARC (TXT) on _dmarc.company.com — start with p=none to monitor, then tighten to quarantine/reject once you confirm legitimate senders aren't breaking.
  7. Add Autodiscover CNAME so Outlook clients auto-configure.
  8. Lower the TTL on records before a cutover (e.g., to 300 seconds) so if something's wrong you can fix and it propagates fast; raise it back afterward.
  9. Cut over MX last, once everything else is confirmed correct — this is the point mail actually starts flowing to the new system, so it should be the final, deliberate step, often done outside business hours.
  10. Validate using Microsoft's built-in domain health checker, plus external tools (MXToolbox is the industry standard for checking MX/SPF/DKIM/DMARC/CNAME all at once).

8. Common Real-World Troubleshooting Scenarios

Symptom Likely Cause Check
Inbound mail bouncing / not arriving MX record missing, wrong, or pointing to old provider nslookup -type=mx company.com
Outlook can't auto-configure Autodiscover CNAME missing or wrong nslookup -type=cname autodiscover.company.com
Legit mail going to recipients' spam Missing/misconfigured SPF, DKIM not enabled, or no DMARC Check headers of a received message for spf=, dkim=, dmarc= results
Domain being spoofed for phishing No DMARC enforcement (p=none or missing) Move to p=quarantine then p=reject
Mail flow works internally but not externally Connector misconfiguration or accepted domain mismatch Exchange admin center > Mail flow > Connectors
DNS changes "not working" TTL caching — old records still cached by resolvers Wait out the TTL, or check with a tool that bypasses cache (e.g., dig +trace)

Useful command-line tools to practice with:

nslookup -type=mx company.com
nslookup -type=txt company.com
nslookup -type=cname autodiscover.company.com
dig company.com MX
dig _dmarc.company.com TXT

10. Why This Matters for AZ-104 and Support Work

Azure Administrator Associate touches DNS through Azure DNS zones and Entra ID custom domains rather than Exchange specifically, but the concepts transfer directly: verifying domain ownership via TXT, adding MX/CNAME records for hybrid identity or mail routing, and troubleshooting propagation delays are all patterns you'll see in both the exam and real tickets. Being able to explain why a record exists (not just where to paste it) is what separates L2 troubleshooting from just following a runbook — and it's exactly the kind of depth that shows well in interviews for cloud/systems engineering roles.
